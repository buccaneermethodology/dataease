## 发现与修复要求

### PR01：能力分母目前只有标签，尚不可逐项对账

严重度 P1；分类 S4 语义歧义 / L2 能力面。`contract-v1.json` 的 frozen_denominator 写“核心6类＋F01–F18＋P0新增可访问能力”，但本次卡绑定材料没有 F01–F18 的名称、来源定位及其与核心六类的映射，也没有 P0 新发现能力清单。source-inventory-v1.json 是 7070 条物理文件记录，不能替代能力分母。stage-plan 明确将能力分母列为 P0 必需产物，故不能据当前文件宣称 P0 已通过。

修复：在 SP-001 内建立稳定能力 ID、名称、来源、核心/非核心类别、K 域、发现依据及待核实状态的逐项表；原有 F 编号从全景参考追溯，但不得据参考直接认定实现；新增能力追加记录。将该表绑定下一版合同。此项阻断 P0 完成和批量提取准入，不阻断只读发现。不能以未知或缺口自动消除核心分母。

### PR02：正式事实/能力/关系合同尚未给出可执行语义

严重度 P1；分类 S5 语义不可验证 / L5 验证面。design-v1.md 仅约定类别和 additionalProperties 禁止，未定义对象字段、必填语义、关系端点类型、来源类别准入、适用条件表达及实施事实与规范事实的区分规则。contract 的 N01–N04/P01 是案例描述，不是冻结输入和预期错误判据。P1 本来包含 schema 工作，因此不要求它现在已经实现，但当前预审不得被解释为未来 schema 自动通过。

修复：P1 首先冻结一个有界对象合同及固定正反例，再做生成/检查实现。至少明确 source_repo/revision/path/digest、symbol/行区间、核实时间、scope、事实类别、关系证据及 ID 唯一性；能力缺失语义字段须显式引用 SP 缺口而非填造结论。规范类记录只声明规范要求，不能被生成器压成已实现行为。测试关系名称/投影明确“测试资产关联，未运行”；静态证据不能产生 tested。固定反例覆盖执行 Dashboard 来源、全景参考直接准入、过期摘要、未证实事实、悬空关系和重复 ID。此项阻断批量正式知识生产，不阻断 schema 设计与候选提取。

### PR03：context 中拓扑理由为无关规则编辑描述

严重度 P2；分类 S2 语义漂移 / L4 协作面。context-v1.json 的 topology.reason 称“根代理完成有边界的规则编辑……不改执行判定”，与本次全仓 KB 构建不一致；route 本身则正确。修复时另存 context 新版本，写明 domain builders、独立内容复核和最终绑定职责，重新生成受影响卡/admission，保留 v1。此项不单独阻断设计，不能在绑定后原地改字节。

## 单行误读与未来代理误用

1. 只看到“schema通过/covered”便认为内容真实：使用“结构通过，语义待复核”，并保留独立判据。
2. 只看到“implemented”便认为无条件可用：生成投影必须显示适用 Profile/身份/入口与“静态源码证实”，不可省略条件。
3. 只看到“F01–F18已对账”便认为核心穷尽：必须展示冻结分母、新增能力和未核实项；目录盘点不得作为语义覆盖数。
4. 只看到“测试覆盖”便认为测试运行通过：改为测试资产关联及未执行状态，测试存在与运行结果分别表达。
5. 把本预审 PASS 当作 KB 验收：报告仅覆盖设计边界；实施入口是 WEAK，独立最终验证与最终 Gate 尚未发生。

无需为这些修复新增产品功能或治理系统；复用现有 SP 文件和阶段，避免将一次 KB 建设扩为通用知识平台。当前没有发现必须要求用户重新授权的范围变更。上述建议均为原范围内合同细化，不改变完成分母。
