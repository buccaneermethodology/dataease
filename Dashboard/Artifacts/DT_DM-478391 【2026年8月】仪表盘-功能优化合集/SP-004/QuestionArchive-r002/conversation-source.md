设计人员希望计算华东地区的平均利润率。

这里存在两种不同的计算方式。

方式一：基于透视表已经展示的产品行计算

AVG(20%, 30%) = 25%

方式二：基于底层订单明细计算

假设产品A的10条订单利润率均为20%，产品B的100条订单利润率均为30%。

例如：

AVG(利润率) = (20% + 30%) / 2 = 25%

优点：符合用户直接对可见透视表结果进行二次汇总的直觉。

透视结果二次计算（Pivot-result Aggregation）

透视结果二次计算：25%。

Q155：F08 自定义汇总表达式是否需要限制计算复杂度？
目前 F08 已确认：

后端计算响应时间目标为 3 秒（REQ-149）。
不使用计算结果缓存（REQ-152）。
这意味着复杂表达式可能产生较高的数据库计算开销。

例如，设计人员编写：

CASE
    WHEN SUM(销售额) = 0 THEN 0
    ELSE ROUND(
        (SUM(利润) - SUM(成本)) /
        SUM(销售额) * 100,
        2
    )
END

这样的表达式比较常见。

但如果表达式包含几十层嵌套函数、数百个字段引用，可能显著影响解析、校验及计算性能。

因此，需要明确是否设置表达式复杂度限制。

A. 设置固定的复杂度上限
例如：

表达式最大长度：2,000 字符。
函数嵌套深度：最多 10 层。
单条表达式最多引用 20 个字段。
超过任一限制时拒绝保存。

这些数值是候选值，尚未经过 DataEase 性能验证。

B. 不设置业务层面的固定复杂度限制（建议）
允许设计人员使用 REQ-136 已确认的函数和运算符自由组合。

不额外限制表达式长度、嵌套层级或字段引用数量。

但必须保留必要的语法校验、权限校验及系统资源保护机制。

C. 根据 DataEase 现有表达式机制确定限制
优先复用现有表达式编辑器、解析器和计算引擎的容量限制。

如果现有机制已有长度、嵌套深度或字段数量约束，则直接沿用。

只有发现现有约束不足以保证系统稳定性时，才提出调整。

D. 通过性能测试确定复杂度上限
先使用不同复杂度的表达式进行性能测试。

结合 REQ-149 的 3 秒指标，确定合理的长度、嵌套深度和字段引用数量限制。

超过验证上限时禁止保存。

避免任意设置限制：目前没有证据证明 2,000 字符或 10 层嵌套是合理上限。
保持兼容性：尽可能沿用 DataEase 现有计算字段的使用习惯。
控制资源风险：不因为开放自定义表达式而取消系统已有的资源保护措施。
需要注意，选择 C 不会取消 REQ-149 的 3 秒性能验收目标。后续仍需通过实际测试验证表达式复杂度对计算性能的影响。
